Section 04

Architecture Highlights

Four decisions that made the product actually work.

Parallel Batches with SSE Streaming

Generation runs as parallel groups of 5 Claude API calls (15 examples each), not one long sequential call. Results stream back to the frontend via Server-Sent Events as each group completes — so you see real progress, not a spinner.

concurrency model
User requests 500 examples

  ├── Group 1: Batches 1–5   (75 examples)  ← fired concurrently
  ├── Group 2: Batches 6–10  (75 examples)  ← starts after Group 1
  ├── Group 3: Batches 11–15 (75 examples)
  ├── Group 4: Batches 16–20 (75 examples)
  ├── Group 5: Batches 21–25 (75 examples)
  ├── Group 6: Batches 26–30 (75 examples)
  └── Group 7: Batches 31–34 (60 examples)

SSE heartbeat every 15s → keeps Cloudflare Tunnel alive
Total wall-clock time: ~70s (vs ~600s sequential)

Persistent Server, Not Serverless

Running on Railway (persistent Node.js process) instead of Vercel serverless means a 90-second streaming request is just a normal HTTP request. No maxDuration configs, no Vercel Pro plan for long-running functions, no architectural workarounds.

Serverless function timeouts would have forced chunking generation into multiple client-initiated requests, adding complexity and failure surfaces. A persistent Railway server running next start makes this a non-issue. The right infra choice eliminates an entire class of problems.

Client-First Labeling State

The labeling page fetches 50 examples into local React state and fires background PATCH requests for every action — never awaited. Failed saves retry silently twice before surfacing a toast. The user is never blocked.

User presses A (Accept)
instant local state update → card slides away
Background PATCH fires
PATCH /api/examples/:id — not awaited
Next example renders immediately
from local queue of 50 — zero network wait
Queue refills in background
when queue.length drops below 10, fetch next 50

Fault-Tolerant Generation

Every raw Claude response is stored before parsing. If JSON extraction fails on a batch, it's retried once. If it fails again, that batch is skipped and logged — generation continues. You never lose the whole run because of one malformed response.

error handling
For each batch:
  1. Call Claude API
  2. Store raw response → DB (before parsing)
  3. Extract JSON → if fails → retry once
  4. If retry fails → log + skip batch → continue

Result: a 500-example run with 1 bad batch returns 485 examples,
not an error. The UI surfaces "14/15 batches succeeded."

Section 07

What I Learned Building This

Four non-obvious decisions that shaped the product.

The Axis Extraction Prompt Is Everything

Getting Claude to identify the right diversity dimensions — ones that actually matter for the domain — is what makes the generated dataset useful rather than just large. A naive prompt produces generic axes. The final prompt gives Claude your schema, your seed examples, and explicit instructions to think about what varies in the real world for that task type.

prompt design
Bad:  "Identify diversity axes for this dataset."
      → Returns: Length, Formality, Topic, Tone, Complexity
      → Generic. Applies to any text task.

Good: "Given this schema and these seed examples, identify 5–8
       dimensions of variation that would cause a model fine-tuned
       on this task to fail differently across each dimension."
      → Returns: Tech Stack, Project Scale, Impact Measurability,
                 Role Seniority, Feature Interdependence
      → Domain-specific. Actually catches real failure modes.

Streaming Is Table Stakes, Not a Nice-To-Have

Without live progress, a 60-second generation feels broken — users assume something failed. With SSE streaming showing "Generated 45 / 200 examples…", users stay engaged and trust the system.

The first internal test had no streaming. Every tester clicked the button, waited 8 seconds, saw nothing, then clicked it again. The second click started a duplicate run. Streaming fixed both the perception problem and the duplicate-run problem simultaneously.

Persistent Server Beats Serverless for Streaming Products

The decision to use Railway instead of Vercel saved weeks of architectural work. Vercel serverless functions have max duration limits (10s free, 60s–300s Pro). A streaming generation request that runs 90 seconds is trivial on Railway and a real problem on Vercel.

Optimistic UI Is the Right Model for Labeling

The labeling UI keeps everything in local React state and fires background saves. The first version awaited every PATCH call before advancing to the next example — 200–400ms of latency per label action. With background saves, the same labeling session feels instant. The UX difference is dramatic.

Background saves with silent retries and toast-on-failure is the right architecture for any high-frequency user action. The user doesn't care about the network call — they care about the item being labeled. Decouple those two things and both feel better.
